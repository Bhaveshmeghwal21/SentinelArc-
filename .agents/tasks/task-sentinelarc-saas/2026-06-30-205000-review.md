# SentinelArc review fixes — hash chain, usage tracking, circuit breaker isolation (v2)

All nine issues from the v1 review have been addressed. The audit hash chain now persists hashes in the payload JSON and strips them on reconstruction, correctly round-tripping through the Prisma store. Usage tracking is wired into the ingestion route as fire-and-forget. The circuit breaker is per-client via a `Map<string, CircuitBreaker>`. The plan naming mismatch is resolved with a centralized `PLAN_KEY_TO_TIER` constant exported from `stripe.ts` and consumed by the webhook handler. Rate-limit headers are removed. Atomic increments replace the read-then-write pattern. The threshold floor is documented in code comments. Five new webhook mapping tests and three usage-tracking integration tests were added.

**Watch for:** The `BillingUsage` table lacks a unique constraint on `(clientId, periodStart, periodEnd)`, so `getOrCreateUsageRecord` can create duplicate records on the first concurrent requests of a billing period (likely). The new-conversation detection (`lastActiveAt === createdAt`) depends on Prisma returning the DB-generated timestamps for new records, which is correct for PostgreSQL but should be validated if the ORM changes (possible).

**Verdict**: APPROVED

## High-level view

The audit hash chain fix stores `_previousHash` and `_entryHash` inside the payload JSON on write, then strips them on read via `reconstructEntry`. The `verify()` method hashes `entry.payload` (post-strip), which matches the payload used when the hash was originally computed in `AuditLogger.log()`.

Usage tracking calls `trackTurnUsage(clientId, isNewConversation)` fire-and-forget after the conversation upsert. The new-conversation heuristic compares `lastActiveAt` to `createdAt` timestamps from the upsert result. One remaining gap: `getOrCreateUsageRecord` does a find-then-create without a unique constraint on the table, so two concurrent first-requests-of-the-month can create duplicate records and inflate counts via `updateMany`.

<details>
<summary>Issues (2)</summary>

1. **Duplicate usage records on concurrent first-of-period requests** — `BillingUsage` has no `@@unique([clientId, periodStart, periodEnd])` constraint. Two concurrent requests at the start of a billing period will both `findFirst` → null, both `create`, producing duplicate rows. Subsequent `updateMany` increments all duplicates, inflating counts. Add a unique constraint or use `upsert`. (likely)
2. **New-conversation detection is timestamp-equality dependent** — `isNewConversation` checks `lastActiveAt.getTime() === createdAt.getTime()`. This works because Prisma returns DB-generated defaults for both fields on create. If the schema ever adds an explicit `lastActiveAt` to the `create` clause, the heuristic breaks silently. Consider having `upsert` return a flag or checking `update` vs `create` path via Prisma's returned metadata. (possible)

</details>

## Usage record creation race

`getOrCreateUsageRecord` performs `findFirst` then `create` without protection:

```typescript
const existing = await prisma.billingUsage.findFirst({
  where: { clientId, periodStart: start, periodEnd: end },
});
if (existing) return existing;
const created = await prisma.billingUsage.create({ ... });
```

The `BillingUsage` model defines:
```prisma
@@index([clientId])
@@index([periodStart, periodEnd])
```

No `@@unique` constraint. Two requests arriving simultaneously at month rollover both see no record, both create one. The `incrementConversationCount` fix uses `updateMany` which would increment *both* duplicate rows, doubling the count for that single event. In practice this is rare (only at period boundaries) and self-heals once one record "wins" subsequent findFirst calls, but it can produce a billing over-count on the exact rollover moment. Adding `@@unique([clientId, periodStart, periodEnd])` and catching the unique violation on create would eliminate this entirely.
