# Real-time AI safety scoring and crisis routing SaaS platform

SentinelArc is a greenfield multi-tenant safety scoring system that ingests conversation turns from AI companion platforms, scores them for risk across six categories (self-harm, sexual content, age signals, emotional intensity, romantic escalation, dependency language), and triggers tiered actions: soft flags for review, hard blocks to interrupt conversations, and crisis routing that delivers hotline resources immediately. The system is built on Next.js 14 with a BullMQ scoring worker, Prisma/PostgreSQL persistence, Stripe billing, and a reviewer dashboard that feeds back into a labeled dataset pipeline for future ML training.

**Watch for:** The Prisma audit log store discards `previousHash` and `entryHash` on write, making hash-chain verification non-functional in production while tests pass using the in-memory store (confirmed). The ingestion API never calls `trackTurnUsage`, so billing usage counters are not actually incremented when conversations are ingested (confirmed). Race condition in the crisis fast-path where module-level mutable circuit breaker state is shared across concurrent BullMQ jobs (confirmed). The Stripe webhook handler maps `GROWTH -> PROFESSIONAL` via a hardcoded mapping that diverges from the billing module's own plan keys, risking silent plan misconfiguration (confirmed).

## High-level view

The scoring pipeline is well-layered: turn-level pattern matching feeds into arc-level trend detection, which feeds into a threshold engine with hard system-minimum floors. The crisis path is architecturally separated from the review queue, ensuring resource delivery even under degraded conditions. The circuit breaker pattern protecting side effects is sound in principle, but the module-level mutable state creates cross-job interference in the concurrent BullMQ worker.

The threshold engine's critical invariant (self-harm >= 0.7 always fires CRISIS_ROUTE regardless of client configuration) is enforced at two levels and validated with property-based tests using fast-check. The inverse problem is that non-crisis thresholds can only be raised, never lowered, which may frustrate clients whose content regularly triggers false positives at 0.5.

Tenant isolation is enforced per-query via `clientId` filtering, though there's no database-level row security to backstop application bugs. The Stripe webhook does signature verification but relies on a JSON path query to find the client by `stripeCustomerId` stored in a JSON settings column, which depends on Prisma's JSON path support working correctly across PostgreSQL versions.

Billing integration has a plan naming mismatch: the Stripe module defines plans as STARTER/GROWTH/ENTERPRISE, but the database enum and webhook handler map GROWTH to PROFESSIONAL. More critically, `trackTurnUsage` — designed to be called from the ingestion pipeline — is never actually invoked, so usage counters stay at zero regardless of ingestion volume.

Test coverage is strong on the safety-critical paths (threshold invariants, crisis routing reliability, audit immutability) but the in-memory test doubles mask a production bug in the Prisma audit store, and there's no coverage for the webhook plan mapping or the usage tracking integration gap.

## Audit hash chain broken in production

The `PrismaAuditLogStore` implementation discards the hash chain data:

```typescript
async append(entry: AuditLogEntry): Promise<void> {
  await prisma.auditLogEntry.create({
    data: {
      id: entry.id,
      clientId: entry.clientId,
      actor: entry.actor,
      action: entry.action,
      resource: entry.resource,
      payload: (entry.payload ?? undefined) as Prisma.InputJsonValue | undefined,
      timestamp: entry.timestamp,
      // previousHash and entryHash are NOT stored
    },
  });
}
```

The `getLatestEntry` method reconstructs from `payload._previousHash`, but nothing ever writes `_previousHash` into the payload. The code even acknowledges this with a comment: "In production, we'd store previousHash and entryHash in the DB." The `InMemoryAuditLogStore` stores the full object including hashes, so all 254 lines of immutability tests pass while the production store is broken.

This means the audit log's tamper-evidence guarantee — a core compliance feature — is not functional. `auditLogger.verify(clientId)` will always find `entryHash: ""` on every entry and report chain corruption on any real database.

## Usage tracking never called from ingestion

The ingestion route (`src/app/api/v1/ingest/route.ts`) performs: validate API key -> upsert conversation -> create turn -> enqueue scoring job -> return 202. At no point does it call `trackTurnUsage` or `incrementConversationCount`/`incrementTurnCount`. The billing usage record will perpetually show zero conversations and zero turns, regardless of actual ingestion volume.

The `trackTurnUsage` function accepts `(clientId, isNewConversation)` — the ingestion route has both pieces of information (it knows whether the upsert created a new record). The integration is a one-line addition but currently missing.

## Shared mutable circuit breaker state

The crisis router uses a module-level `DB_CIRCUIT_BREAKER` object shared across all concurrent BullMQ jobs (concurrency: 10). When a dependency fails, `recordFailure` increments the counter. After 3 failures across *any* jobs, the circuit opens for *all* jobs for 30 seconds. During a burst of crisis events with a transient DB outage, the circuit opens after 3 failures and then suppresses `logCrisisEvent` for all subsequent crisis routes, creating an audit gap. Resource delivery is unaffected (fire-and-forget design protects it), but crisis events won't appear in the database for that window.

## Ingestion API rate limiting gap

The ingestion endpoint returns static rate-limit headers:

```typescript
headers: {
  "X-RateLimit-Limit": "1000",
  "X-RateLimit-Remaining": "999",
  "X-RateLimit-Reset": String(Math.floor(Date.now() / 1000) + 3600),
}
```

No actual rate limiting is implemented. A client sending 100K turns/second would queue them all to BullMQ, potentially exhausting Redis memory and starving other tenants' scoring jobs. The headers create a false contract — a well-behaved client reading these headers would never throttle itself.

## Plan tier naming divergence

In `src/lib/billing/stripe.ts`, plans are keyed as `STARTER`, `GROWTH`, `ENTERPRISE`. The billing API POST endpoint accepts these exact strings and stores the plan name in Stripe subscription metadata. But in the webhook handler:

```typescript
const planTierMap: Record<string, string> = {
  STARTER: "STARTER",
  GROWTH: "PROFESSIONAL",
  ENTERPRISE: "ENTERPRISE",
};
```

The database `PlanTier` enum is `FREE | STARTER | PROFESSIONAL | ENTERPRISE`. This mapping lives only in the webhook handler. If the billing API's POST handler is extended to also update `planTier` directly, someone could write "GROWTH" which isn't a valid enum value. The asymmetry between customer-facing plan names and database tier names has no centralized definition, no type safety, and no test.

## Usage tracking increment race

`incrementConversationCount` reads the current count, then writes `count + 1`:

```typescript
const record = await getOrCreateUsageRecord(clientId);
const updated = await prisma.billingUsage.updateMany({
  where: { clientId, periodStart: start, periodEnd: end },
  data: { conversationCount: record.conversationCount + 1 },
});
```

Two concurrent requests both read `count: 5`, both write `count: 6`, losing one increment. The fix is `{ conversationCount: { increment: 1 } }`. This matters for billing accuracy at scale.

## Threshold enforcement asymmetry

For crisis thresholds: `Math.max(SYSTEM_MINIMUM, Math.min(clientValue, 1.0))` — client can only raise above the minimum.

For non-crisis soft flags: `Math.max(clientValue, DEFAULT_VALUE)` — client can only raise above the default (0.5). A mental health platform with clinical discussions that generates false positives at 0.5 emotional intensity cannot lower its threshold to reduce noise. The system forces all clients to the same sensitivity floor for soft flags — a product decision that isn't documented in the API response or README.

## Test coverage gaps

Not tested: the Prisma audit log store (hash persistence bug), webhook plan-tier mapping, usage tracker concurrent increment behavior, actual rate limiting (none exists), dashboard UI components, the ingestion-to-usage-tracking integration (it doesn't exist), compliance export date filtering edge cases.
